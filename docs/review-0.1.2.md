# 第二轮现实场景审查：v0.1.2

本轮从 v0.1.1 继续检查，只修改具备具体触发路径、能用隔离测试复现的问题。没有增加配置项，没有操作真实 QQ 群。

| 实际触发条件 | 原有问题 | 本次处理 |
| --- | --- | --- |
| 正在查询机器人身份或管理员权限时，保存了新的群规则或机器人 QQ | 旧 `Policy` 可能搭配新配置版本保存计划；模拟中旧机器人仍提交了移出 | 计划开始前核对规则与当前配置一致；授权期间版本改变则取消；执行入口再次核对配置指定的机器人 |
| 管理员刚禁言候选成员，接口仍返回旧的未禁言状态 | 只查询禁言字段，忽略已收到的 `group_ban` 通知；全员禁言的 `user_id=0` 被身份过滤丢弃 | 持久保存成员/全群禁言通知，结合接口判断；消息版本检查覆盖最后一刻的禁言变化；成员禁言自然到期，不把禁言操作计为成员发言 |
| 连续读取的第一次名单含近期发言、管理员、头衔或禁言信息，第二次来自较旧缓存 | 第一次只参与比较 QQ 集合，其保护证据被丢弃 | 合并两次读取的保护信息，发言证据持久保存；依赖字段缺失仍保留；入群时间冲突则暂缓 |
| “保留”命令处理中发生重载、进程退出或保护名单写入失败 | 操作已被记为人工处理，永久保护却可能没写入，之后重新入群失去保护 | 人工处理记录、永久保护、审计记录放在同一个 SQLite 事务里，一起提交或回滚 |
| 数据库写入时任务被取消，同时磁盘写入失败；或重载与关闭重复取消同一任务 | 取消分支没有标记存储故障，重复取消可能提前结束等待 | 等待已交给数据库线程的事务结束；取消期间的 SQLite/磁盘错误仍标记存储不可用，再保持任务取消状态 |
| 群通知已在事件循环排队，移出请求尚未开始执行 | 最后检查在网络任务调度前；Python 3.10 的 `wait_for` 可在检查后先处理通知，再继续发送旧决定 | 各 Python 版本统一显式调度网络任务，把最终检查和“已发送”标记放进任务内部，紧接调用传输；取消时未发送的意图不占额度 |

禁言行为依据 OneBot 的 `group_ban`、`duration`、`ban/lift_ban` 约定，并核对 [NapCat 的通知定义](https://github.com/NapNeko/NapCatQQ/blob/main/packages/napcat-onebot/event/notice/OB11GroupBanEvent.ts) 与本机 AstrBot 的 `on_notice` 转发源码。禁言保护仍遵守群配置中的原有开关。

断线可能导致解除全员禁言的通知遗漏。因此已知的全员禁言不依赖旧缓存自动清除：管理员确认群里已解除后，可使用现有的 `/群清理 恢复 群号`。插件两次检查平台的全员禁言状态，并确认期间没有新的禁言通知，再解除该记录、作废旧计划并冷却。平台仍显示禁言或状态未知时不会恢复。

新增测试覆盖上述失败路径，以及通知乱序、禁言到期、重载持久化、关闭禁言保护、恢复途中再次禁言等正常与异常分支。旧版的复现测试确实出现了错误移出、保护状态丢失或提前退出等待；修复后的测试禁止这些结果。

读取额度不足、成员资料缺失、名单人数不一致、移出结果无法确认等已有停止策略继续保留。这些情况不能通过放宽判断来维持自动执行。没有加入额外探测接口或扩大请求频率。

仍无法消除 NapCat 未报告/尚未交给插件的事件，以及实际网络传输开始后到 QQ 服务器执行之间的变化；最终接口没有原子条件移出能力。
