# 工程行为与异常处理

本文描述 v0.2.0 已实现的行为。原方案中的扩展不代表已经交付，见 [设计文档](design.md)。

## 执行路径

```text
生成计划 → 预览 / 等待确认 / 自动就绪
→ 群锁与账号锁 → 检查时段/额度/暂停
→ 持久化批次间隔 → 每人随机等待
→ 可选共享协调器 → 在线、账号、权限与单人资料复核
→ 人数/保护/活动/配置再次检查
→ SQLite写前意图与额度一起提交
→ 实际发出一个普通移出请求
→ 等待通知 → 只读核对 → 已证实 / 观察到缺席 / 结果不明
```

计划过期、配置改变、群/账号绑定改变、确认人不再有管理权限会阻止执行。确认与自动都经过同一个执行器。候选变化只跳过；目标人数已达到则结束周期。名单外的人不会临时补进来。

## 无写入重试

| 操作状态 | 含义及后续 |
| --- | --- |
| submitted | 写前意图已落盘，可能已发出；重启转 unknown |
| confirmed_removed | 收到该账号踢人通知，且时间、成员代次匹配 |
| observed_absent | 两次名单一致且与群人数一致，成员缺席；不能归因于本插件 |
| unknown | 超时、异常或无法证实离群；暂停账号并保留记录 |
| reviewed_retained | 管理员明确决定保留，永久保护，不再重发 |

`status=ok` 不直接算踢人成功。默认等通知 10 秒；无匹配通知时，读取两次名单（间隔至少 2 秒）并核对群详情人数。名单冲突或仍在群则保持 unknown。

写前意图包含计划、账号、群、QQ、入群代次和提交时间，唯一约束阻止同一成员代次再次提交。已经进入网络路径的请求，无论失败还是未知都占最近24小时额度。可以明确证明尚未发送的取消会释放意图和额度。

写前落盘后进程直接退出，即使请求可能没发出，也保守记为 unknown。没有 QQ 服务端幂等键，因此不能承诺 exactly-once。不得删除数据库来强迫重试。

人工“核对”仅重复只读验证，不发移出请求。“保留”记录操作者并加入永久保护；处理完未决记录后，管理员显式恢复。已发送请求无法撤销。账号异常暂停记录来源群，其他群管理员不能越权解除。

人工保留、永久保护和审计使用同一事务，避免取消或磁盘错误导致只处理了一半。网络任务显式调度，最终检查在该任务内部紧接传输调用，覆盖已排队的状态通知。

## 平台一致性

`get_group_detail_info` 用于人数检查；`get_group_member_list(no_cache=true)` 不能保证立即刷新，计划和缺席核验均使用两次一致名单并对照人数。成员角色、入群时间、等级、活动和保护在操作前重新读取。

禁言保护同时检查群详情的 `group_all_shut`（NapCat 使用 -1 表示开启、0 表示关闭）。全员禁言或状态未知时暂停整群清理，计划和最后提交前都检查。请求的群号和QQ号按 NapCat 的字段约定传字符串。

`group_ban` 通知持久保存成员禁言期限及全员禁言状态（`user_id=0`），抵抗旧接口缓存；按通知时间处理乱序。解除全员禁言通知遗漏时，只能由管理员使用“恢复”两次核验平台已解除，且期间无新禁言通知，随后作废计划并冷却。禁言通知不作为成员自身发言计时。

两次名单中查到的活动、管理员、头衔、禁言及较高等级保护证据合并；依赖字段不完整时仍保留。入群时间冲突则暂缓。查询期间保存新配置会取消旧策略，不能把旧策略标记为新版本。

综合评分只改变已符合条件成员的顺序。默认QQ权重为0，不为排名补查QQ资料；显式设置QQ等级上限或正权重仍走现有有界补查和缓存路径。评分及权重进入计划记录，权重改变会使旧计划失效。开启维度缺失时保留，不用0分或重新分配权重推算。

每个已观察成员保存入群代次。入群、退群通知和入群时间变化使旧计划失效。离群记录不会被旧列表恢复成在群；入群时间缺失或回退不新建代次。入群通知先等待匹配的入群时间，向后的时间修正也从本次观察开始保护。平台查到过的最近发言时间和实时活动只增不减。事件指纹去重，乱序活动取最大时间。已收到的撤管理员/退群通知阻止旧权限缓存继续授权；升管理员通知可保护目标，但不会单独授予命令权限。

最终检查与服务器执行之间仍有竞态；平台没有原子“满足这些条件才移出”的接口。两次一致名单也不能数学上证明没有缓存问题。实际运营必须理解这个边界。复核到最后发请求超过30秒会取消本次操作，避免长时间排队继续使用旧资料。

## 限速、调度和恢复

- 定时检查约 30～35 分钟；未达开始人数时只查人数，手动预览可看条件但不执行。
- 每群一个工作锁，每个账号一个批次执行锁；按最早到期顺序，最多4个群独立检查。一个群的长等待不阻塞其他群；同账号的移出仍串行，长等待不占数据库事务。
- 每个接入最多读取180次/小时：后台最多用120次，执行复核可用至150次，最后30次留给管理员授权与核对；预算写入SQLite，重载不清零，读取之间等待1.5～3秒。接口超时25秒，无立即读重试；一般检查错误后等待1小时。
- 单个 QQ 等级补查每轮最多20人，缓存7天并绑定入群代次；每名成员查询成功即保存进度，单个失败缓存6小时并暂缓当前任务，避免重复卡在同一个UID。尚未尝试补查完全部初筛候选时不生成执行名单。
- 账号与群的滚动24小时提交额度、群批次间隔、写入预约、暂停和恢复冷却落盘。读取预算同样持久保存，额度不足时按实际窗口到期时间安排下一次检查。
- 普通启动/重载默认缓冲30～90秒，连接或异常恢复默认冷却300～900秒，均在执行节奏中配置。已有更晚预约不会缩短，包括升级时旧版的启动预约。恢复丢弃旧计划，重新冷却；重载后旧确认作废。
- 反向WebSocket替换、观察到QQ离线/恢复或接入变化使旧计划作废。接入的离线状态与恢复截止时间持久保存，读取失败时也保存冷却；正常停止保存只在同步连接检查中观察到的变化。新接入恢复这些记录，防止短重载绕过恢复等待。截止时间在SQLite串行事务中只延后不提前。请求显式绑定QQ身份，拒绝同一接入多个QQ；未被任何接口或事件观察到的QQ状态变化仍无法保证识别。
- 离线停止当前任务，写入中断或未知结果暂停账号。读失败不会被解释为成员不存在，不自动登录、不自动试探接口安全阈值。
- 系统时钟前后跳变超过2分钟停止执行；启动时若时间早于上次记录也停止。内部时段固定北京时间，用户不需要配置时区。

同一 AstrBot 进程有 `_qq_automation_guard_v1` 时复用其 `run`，使用现有插件实际使用的 `platform_id` 键。长准备等待在共享锁外，最后复核和写入在锁内。共享对象不存在时本插件独立限速；不创建或替换其他插件的私有状态。版本不兼容时停止。

共享锁只提供同进程同接入串行，不能把本插件限额推广到其他插件，也不覆盖所有框架消息发送。检测本机同 QQ 多个接入时拒绝使用；其他主机无法检测，要求一个 QQ 只运行一个自动清理实例。

## 存储与生命周期

```text
data/plugin_data/astrbot_plugin_qq_group_cleaner/
  state.sqlite3
  state.sqlite3-wal / state.sqlite3-shm   SQLite自行管理
  instance.lock
  logs/cleaner.log
  logs/cleaner.log.1 ... cleaner.log.7
```

SQLite 在专用单线程执行器中访问，WAL + FULL synchronous，短事务，5秒 busy timeout。异步取消等待已提交的存储调用结束，再关闭数据库和释放实例锁；不留旧工作线程在新实例启动后继续执行。

同一任务被重复取消也要等到数据库调用完成；取消期间的 SQLite/磁盘错误仍标记存储不健康，随后保留任务取消状态。

实例锁在 Linux 使用 flock，Windows 使用 msvcrt 非阻塞文件锁。同一个数据目录第二个执行器不会启动。此锁不是跨主机分布式锁。

v0.1.1将数据库语义版本从1升级为2，保留已有额度、保护和审计，增加“入群待核验”的身份状态。旧v0.1.0会拒绝打开新库，避免降级时误读状态。不能通过删除数据库强行降级。

停止生命周期取消并等待调度任务、群工作任务和活动命令任务（不等待调用者自身），再关闭数据库、日志和锁。初始化被取消也完成清理；checkpoint、日志flush失败仍关闭连接并释放实例锁。配置非法、数据库损坏/新版本、日志异常、磁盘不足都停止执行。启动失败不回退到空数据库或无审计模式。

状态表保存最近活动时间，不累计聊天正文或完整用户资料。数据库调用积压超过512项、内存活动版本超过10万项时停止；不静默丢掉已收到的近期活动再继续踢人。

## 日志和容量

v0.2.3起默认完整记录每次处理，不需要新配置，独立于 AstrBot 和 NapCat 的日志设置：

| 文件 | 内容 |
| --- | --- |
| `cleaner.log` | 启停及生效配置、检查起止和人数门槛、计划汇总、管理员命令与处理结果、补查和缓存、接口名/耗时/返回码/必要字段、随机等待截止时间、执行前复核、提交意图、发送中断、离群核验、通知确认、账号暂停及全部异常 |
| `screening.log` | 每名已评估成员的数据、评估时间、保护依据、是否符合条件、得分、排序键、排名、是否进入本批及原因；需要QQ补查时还记录初筛；发言活动仅保存标识和时间等元数据 |

每条新增记录是一行JSON，含带`+08:00`时区的北京时间、级别、运行实例`session`。`check`、`plan`、`operation`、`request`、`command`分别关联检查、计划、移出操作、接口调用和管理员命令；有对应上下文时记录账号、群号、QQ号、操作者。上下文按异步任务隔离，重载产生新实例编号。按同一个`plan`搜索两份日志即可追溯成员为何入选以及最终是否移出。筛选记录使用实际评估结果，不为了写日志重新评分；计划保存失败或随后配置变化时，会留下对应计划失败记录，不能把筛选入选等同于已执行。

相同事件逐次落盘，不去重、不截断原因。异常记录包含类型、脱敏后的消息、完整因果链及每层调用的文件/行号/函数，不记录堆栈局部变量或源码行。平台原始完整响应、聊天正文、昵称和认证凭证不写入日志，URL及常见凭证字段脱敏。日志含审查必需的QQ标识与等级、时间、头衔等规则数据，请只向需要排查的人提供。

两份文件分别以20MiB为轮转目标、最多7个归档，合计通常约320MiB。单条记录不截断，因此大记录可能使文件暂时超过目标大小。不按时间删除日志归档；达到归档数量上限后，下次轮转淘汰最旧的一份。数据库审计另按以下策略保留，需要长期存档可在轮转淘汰前收集日志。

任一日志写入/轮转失败都会标记不健康，下一道执行检查阻止提交；首次文件写入故障的原始原因还输出到宿主错误日志。写前意图和结果仍以SQLite事务为准：接口返回成功不等于成员已离群，取消后的在途请求不得仅凭日志中“取消”就认定未发送。日志没有新增网络查询，也不会为了验证日志主动移出成员。重载时关闭并移除两份日志处理器，一份关闭失败仍清理另一份。

每日维护：

- 事件去重指纹、独立审计事件、计划和操作历史长期保留，不再按记录年龄或成员入群代次变化自动删除。
- 维护仅执行被动WAL checkpoint，不做历史数据清理或分库轮转；业务冷却、计划有效期和临时保护期限仍按原规则生效。
- 最近活动、保护和必要成员状态保留，以维持跨重载保护；首版没有导出文件。
- 数据库/WAL合计超过512MiB或磁盘空闲低于256MiB时停止清理，不删除未决记录腾空间。SQLite文件不能当普通日志轮转。

## 验证与未验证部分

测试覆盖规则边界/未知字段、表单默认值、权限/跨账号、等级补全预算、人数回落、等待时的活动和身份变化、配额/并发、写前意图、超时/取消/重载、实例锁、日志轮转和插件入口生命周期。

命令及平台适配器使用隔离模拟，不连接 NapCat，不发 QQ 消息，不移出真实成员。GitHub Actions 在 Windows/Linux、Python 3.10/3.12 运行同一套测试；通过情况以 Actions 结果为准。

本机 Windows 的 Python 不能从当前 Linux 工具环境直接执行（Exec format error），所以没有声称完成桌面实例重载、真实UI保存或 Windows 本机文件占用联调。框架接口依据安装源码逐项核对，入口测试用隔离框架替身。真实QQ的最后联调仍需专门授权测试群。
